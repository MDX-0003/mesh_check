## 摘要

**「不应该存在的组件」**——它有两种空间形态：与主体分离的**悬浮**、与既有表面位置重合的**共位**。

- **检出 424 条**：待人工复核 256 条（悬浮 129 / 共位重叠 102 / 非核心 25）+ 部件贴合界面 168 处

  待人工裁决 17 个 / 确定不通过 0 个——**管线只报告，不自动修改任何几何**。
- **方法**：两套独立几何引擎并行（Blender 原生 + trimesh），画面由前者出、结论由后者出，
  两者的差异本身作为证据使用（第四节给出实测的一致/不一致清单与每个数字的来源）。
- **可复核性**：每条待复核检出都带逐条图证（组件独立渲染三视图 + 定位图），
  本说明另附 8 条抽样复核的逐条判读（第三节）。

## 一、prompt 是怎么选的

**设计原则**：用同一批 prompt 同时覆盖"形态谱系"与"已知缺陷类型"，使评估结论可外推到别的类别，
而不是只看一类物体好不好；同时**追问句保持一句名词性短语**，把"怎么造"留给生成器。

- **16 个多类别日常物**（`expect_floater=false`，14 个类别）：家具 / 餐具 / 家电 / 包袋 / 鞋靴 /
  车辆 / 雕像 / 植物 / 乐器 / 电子 / 生物 / 街道设施 / 户外 —— 刻意跨越硬表面与有机体、单件与多件、
  细柄薄壁与对称形态。
- **4 个悬浮诱导 prompt**（`expect_floater=true`，`category=float-inducing`）：热气球、水晶吊灯、
  举球角色、风铃。这四类在多件生成下天然含"靠绳索/吊挂连接、或与主体分离"的结构，用来**检验
  检出器会不会把设计意图误判成缺陷**——验证点是"该报的报、不该报的不报"，不只是"能不能报"。

**为什么只给一句名词短语**（不用长句描述材质/风格/尺寸）：本批要评估的是**生成器自身的几何质量**。
一旦把材质、风格、构成写进 prompt，评估结论就变成"prompt 服从度"，几何缺陷会被 prompt 掩盖；
名词短语让同类物体在不同模型间保持可比。尺寸同理——不指定尺寸，生成的资产才能暴露"归一化口径"
差异（这也是本项目把模型统一归一化后再渲染的原因）。

**档位对照**：同一批 20 条 prompt 在 **standard（`meshy-7`，20 credits/件）** 与
**smart-topology（5 credits/件）** 两档各生成一遍（40 个模型，prompt 文本逐条一致），
本批交付的是 T2（smart-topology）档；standard 档作对照，用于回答"便宜的档位差在哪"
（p01 两档实测：standard 档单一组件、水密、零检出；T2 档 11 个组件、6 条真非流形边
+ 33 条开放边界 + 515 个自交面，几何明显更脏）。

## 二、这批模型的评估结论

**批次与成本**：T2 档 20 件全部 SUCCEEDED（面数 `target_polycount` 按档位上限显式设为 15,000）。
`data/tasks.json` 口径：`preset=smart-topology`
共 **21 个任务 / 105 credits**（含 1 个不入批次的探针任务 `probe-poly15k`），故**交付的 20 件本体
= 100 credits**；standard 对照批 20 件 = `20 × 20 = 400 credits`。

**检出分布**（`data/findings.jsonl`，T2 全 20 件，共 424 条）：

| 类别 | 条数 | 涉及模型 | 说明 |
|---|---|---|---|
| 悬浮碎片（review） | 129 | 3（p06 / p11 / p18） | 与主体完全分离的组件或整组 |
| 组件重叠（review） | 102 | 14 | 真重叠 50 + 灰区 52 |
| 非核心检出（review，低优先） | 25 | 11 | 紧贴主体、尺寸小、无同类尺寸件，与设计件难以区分 |
| 部件贴合界面（keep，非缺陷） | 168 | 17 | 多件拆分时对接界面顶点重合，属导出特性 |

**几何基础质量的批次分布**（Blender 口径 `blender_checks.json` 20 件全量；trimesh 口径见第四节）：

| 指标 | 结果 | 备注 |
|---|---|---|
| 面数 | 4,254 ~ 16,601 | 20 件同量级，档位一致性好 |
| 真非流形边（>2 面共用） | 17/20 件 > 0，中位 5，最大 63（p15） | 量级小；不污染渲染，留档 |
| 表面自交面 | **20/20 件 > 0**，34（p10）~ 5,263（p15） | 纯渲染不可见；抽样归因见下 |
| 零面积面 | 14/20 件 > 0，0 ~ 86（p15） | 顶点级退化，留档 |
| 零长度边 | 仅 1 件（p15，1 条） | 同上 |
| 水密 | **0/20** | T2 输出普遍非水密，低模壳体形态属常态，不视为缺陷 |
| 绕组一致 | 18/20（p15、p20 不一致） | 与自交面高的模型重合，留档 |

**自交面与组件检出不是同一件事**：两者只有中等相关（自交面最多的 p15 有 5,263 个自交面、
30 条组件检出，而 p08 自交面 3,736 却 0 条检出）。归因显示：p11 的交叠对 96.6% 为**跨组件**、
其中 98.6% 涉及 <100 面的小组件，即自交主要是"重复面片/碎壳穿过主体"的**伴随读数**；
而 p02 这类干净模型的 441 个自交面来自壶嘴/把手与壶体的有机衔接（同组件曲面折叠），
属生成式网格拼接的**良性基线**。故本批把自交降为伴随指标，不当独立检测问题。

**结论要点**：

1. **两个真实存在的系统性问题**：**组件重叠**（14/20 个模型存在两套表面叠于同一位置，渲染时
   来回闪烁）与**悬浮碎片**（高度集中在 3 个模型：p06 鞋、p11 钢琴、p18 吊灯）。
2. **"多件"本身不是缺陷**：168 处贴合界面属 T2 拆件的正常形态，只计数、不进复核队列。
   若把所有"表面贴着"都算作缺陷，结论会变成"19/20 个模型有问题"——分型口径直接决定这个数字。
3. **几何基础质量可用但不干净**：非流形边、自交面、零面积面在每个模型的量级都很小（除 p15），
   且**渲染不可见**；它们与本批选定的检测问题（组件级）是两个层面的东西。
4. **落位**：确定通过 3 / 待人工裁决 17 / 确定不通过 0。判据只看是否留有**待复核检出**
   （贴合界面这类非缺陷不计入）；任何一条检出都能被人工推翻，"不通过"只能由人工给出。

## 三、为什么选"不应该存在的组件"做自动检测，效果如何

**为什么选它**（对照五个维度：下游损害 / 发生率 / 单实例严重性 / 可检测性 / 可行动性）：

- **下游损害直接且可解释**：本项目的下游是"渲染式训练场景搭建"。悬浮组件会在渲染图中以
  **幻影物体**出现（可能被误标注为真实实体），共位重复面片是 **z-fighting 闪烁**的来源——
  这两类是唯一会直接改变渲染像素的缺陷；自交、非流形、零面积、开放边界在本批的光栅化
  渲染下不产生可见差异，代价出现在仿真、打印这类下游。
- **发生率**：悬浮单独看不普遍（3/20），但与之合并定义的"贴着"形态（共位重复）出现在
  **19/20** 个模型上；按"有待复核检出"计为 **17/20**——自动检测的价值随发生率成立。
- **判据客观可复现**：悬浮用几何距离（视觉岛 + 疏离度），共位用"焊接后连通性消失 + 表面积
  重叠率"双证据，不依赖主观观感，且每条都能用像素级图证对号入座。
- **可行动性完整**：处置链条明确——高置信者可删、其余进人工复核（每组件独立渲染图量化特征与白话理由），
  **不把不确定伪装成结论**（本批 0 个自动处置）。

**与备选检测项的对照**：

| 备选问题 | 本批实测 | 为什么不选 |
|---|---|---|
| 碎片化（视觉连续的表面碎成大量壳） | 普遍（p11 306 壳 / p18 342 壳） | 渲染基本不可见（缝隙在像素以下），是资产质量度量而非数据污染；转为岛层顺带产出的度量 |
| 表面自交 | 普遍且数值大（p15 5,263 / p11 4,705 面） | 纯渲染不可见（穿插不影响深度合成）；且多为跨组件小件穿过主体的**伴随读数**，自身基线噪声大 |
| 非流形边 | 17/20 件 > 0，最大 63 | 渲染不可见，仅模拟/打印类下游有害；当前无低成本自动修复方案 |
| 开放边界（非水密） | 20/20 非水密，最大 1,905 条 | 低模/壳体形态的**常态**而非异常，不构成独立"问题" |
| 零面积面 / 零长度边 | 14/20 件有零面积面（0~86） | 顶点级清理即可，渲染不可见，不值得一整个检测问题 |
| 法线朝向 / UV 类问题 | 本批未作为候选 | 法线一致性问题在本批为 18/20 一致（余 2 件与自交高的模型重合）；UV 属贴图范畴，任务限定几何质检 |

**检出机制**（两路并联，都只报告不修改）：

- **悬浮检出**：把组件按空间邻近聚成**视觉岛**（单连接聚类，ε = 3% 模型对角线；42 个模型上
  实测 2%~5% 区间内结果稳定，取区间中点），岛与主体完全分离即报；判据取"主组件对角线的比例"，
  故跨类别免调参。
- **共位检出**：以"焊接后连通性消失"+"表面积重叠率"双证据判定，再按重叠率分型为
  **真重叠（≥60%）/ 灰区（20%~60%）/ 贴合界面（<20%）**——第三类只计数、不进复核队列。
  阈值取值有几何依据：**任何界面贴合形态的"面积重叠率"上限约 0.5**（两个立方体对接的界面
  = 1/6 ≈ 0.167），故 0.2 是"非缺陷"的安全线，0.6 才是"两套面真的叠在一起"。

**效果**：

- **覆盖率**：4 个悬浮诱导 prompt 全部被识别；p18 吊灯 20 个垂挂水晶真部件**全部保留**、
  只报真正的碎屑，说明设计意图没被误杀（相对阈值跨类别免调参的直接证据）。
- **可复核性**：256 条待复核检出 **100% 带逐条图证**（单件隔离渲染补位，仅单引擎可见的组件
  同样有图）。
- **可解释性**：每条检出的证据、量化字段与白话理由都在明细页，人工可逐条推翻。

**抽样复核（8 条，交付方按图证逐条判读）**：按类别分层抽样（悬浮 2 / 真重叠 3 / 灰区 2 /
非核心 1），层内按面数从大到小取（即偏显著件）。判读结论如下：

| # | 检出（口径） | 图证判读 | 判读结论 | 与检出一致性 |
|---|---|---|---|---|
| 1 | p06#1 悬浮·整组（42 件同岛，距主体 0.109 倍对角线） | 定位图里高亮的是一整只鞋，幽灵是另一只 | **非缺陷**：prompt 是"一双运动鞋"，两只鞋天然分离 | 检出正确，结论应被推翻（"只检出不删除"的用例） |
| 2 | p11#6 悬浮·整组（86 件同岛，0.048） | 钢琴几何密集，贴近面板被半透明壳层填满，306 面的目标（占比 2%）不可辨 | 图证不足以判读 | 存疑 |
| 3 | p15#9 共位·真重叠（93.4%，132 面，贴包围盒薄片） | 贴近面板出现大片品红 = 与邻居重合的那一片 | **真重叠成立**；同时属"贴包围盒的无厚度薄片" | 一致 |

| 5 | p04#24 共位·真重叠（100%，6 面） | 细杆穿过邻居表面，重合段呈品红 | 同 #4：重合成立，但为微小片 | 一致 |
| 6 | p20#12 共位·灰区（25.8%，214 面，邻居=主体） | 目标位于幽灵内部，图为包裹视角 | 贴合/穿插关系不可见 | 存疑 |

## 四、用了什么方法：两个几何引擎的分工、一致与不一致

本项目**同时**使用两个几何引擎，不是冗余，而是分工 + 互证：**画面由 Blender 出，结论由 trimesh 出，
两者的差异本身作为证据使用**。本节把"哪里一样、哪里不一样、页面上的每个数字来自谁"讲清楚。

### 4.1 两个引擎各自承担什么

| 引擎 | 运行位置 | 承担的工作 |
|---|---|---|
| **Blender 5.0.1**（bpy / bmesh，`--background` headless 运行） | `meshq/blender/` | **全部渲染**：三视图三通道（平滑 / 判别着色 / 线框）、组件独立渲染、逐检出定位图；**一份原生几何指标**：面/顶点数、边分类（开放边界 / 真非流形）、自交面（BVH 自相交）、零面积面与零长度边、组件连通域、归一化参数 |
| **trimesh**（+ numpy / scipy，虚拟环境） | `meshq/core/mesh_ops.py` 等 | **全部判定**：组件划分、视觉岛聚类、最近距离、表面积重叠率、共位分型、悬浮/共位检出与落位；**一份复核指标**：面/顶点、边分类、水密性、欧拉数、退化面、组件特征 |
| 纯投影打分（numpy，`meshq/core/locator.py`） | 虚拟环境 | 定位图的**观察方向选择**（半透明灰底使遮挡不再是约束，故用投影面积/朝向打分择优，不跑射线） |

两套引擎的**算法不同源**：同一模型可能给出不同的组件划分与边计数——这一点被**有意保留**，
因为"存在性依赖焊接容差的候选"正是不该自动处置的对象（差异即证据）。典型用例：p12 的一个
65,848 面部件，trimesh（焊接 1e-5 量化）判**分离**、Blender（焊接 1e-4 邻近合并）判**连通**，
双引擎冲突 → 该模型转人工裁决，而不是冒险自动删除。

### 4.2 实测：哪些量一致、哪些不一致（T2 全 20 模型逐件对照）

| 量 | 一致模型数 | 不一致时的差异量级 | 说明 |
|---|---|---|---|
| 面数 | **7 / 20** | 1 ~ 18 面（0.01%~0.1%） | Blender 焊接更强，会额外并入极少数退化面 |
| 真非流形边（>2 面共用） | **15 / 20** | 1 ~ 7 条 | 多数模型为 0，分歧是个位数 |
| 开放边界边 | **11 / 20** | 2 ~ 21 条（0.2%~4%） | T2 低模普遍非水密（最大 1,905 条），小差异来自焊接不同 |
| **组件数** | **1 / 20** | Blender 系统性更少：p18 237 vs 342、p11 291 vs 306、p15 107 vs 144 | 见 4.3；这是最大且唯一"系统性"的差异 |

要点：**"边与面"级别的量在两套引擎下高度一致（差异在千分之几），"组件划分"级别则系统性不一致**。
换句话说，几何量的复核可以直接用第二引擎对账；而组件级结论（编号、件数、检出）必须固定一个口径。

### 4.3 组件数为什么必然不一致，以及本项目如何处理

根因是两者的"焊接"不是同一个算子：

- **Blender**：`mesh.remove_doubles(threshold=1e-4)` —— **邻近合并**（两点距离小于阈值即合并）；
- **trimesh**：`merge_vertices(digits_vertex=5)` —— **十进制量化后精确去重**（把坐标量化到 1e-5
  再删重复点），它**不是**邻近合并。

因此**不能用 trimesh 的 digits 去模拟 Blender 的阈值**（实测反例：p18 在 digits=4 下组件数反而
从 24 变成 29——量化位移导致去重失败）。本项目的处理是**不对齐、只固定口径**：

- **编号口径统一取 trimesh**：页面上的 `#rank`、明细表面数、逐组件 GLB 文件名、组件独立渲染图
  全部同源，读者看到的编号与文件一一对应；
- **Blender 口径的组件数**作为原生产物随模型分发（`blender_checks.json` 的 `n_pieces`），
  用于对账，**不参与页面编号**（早期混用会造成"结论说 8 个组件、表里出现 #10"）。

### 4.4 交付页上每个数字与每张图分别来自哪个引擎

| 页面/产物上的内容 | 来源 |
|---|---|
| 结论句"本模型共 N 个组件"、明细表 `#rank` 与面数 | **trimesh**（`pieces/manifest.json` / `findings.jsonl`） |
| 计数盒：悬浮 / 重叠面 / 非核心 / 贴合界面 | **trimesh**（检出结果） |
| "问题"列白话、证据旁注（重叠率、间隙比） | **trimesh**（展示层函数据检出数字生成） |
| 落位（确定通过 / 待人工裁决 / 确定不通过） | **trimesh** 检出 + 人工裁决 |
| 组件独立渲染图 / 定位图 / 线框三视图 / 干净渲染 | **Blender** 渲染 |
| 定位图里的三色分隔（含品红"与邻居重合的那一片"） | **Blender**：逐面"面质心到邻居表面的最近距离 ≤ 容差" |
| 定位图上的标记环（保证极小件也找得到） | 环的位置来自 **Blender** 投影出的像素框，交付层用 Pillow 画环 |
| 定位图的观察方向 | `meshq/core/locator.py` 纯投影打分（虚拟环境侧，读 trimesh 载入的三角面） |
| 每模型附带的 `blender_checks.json` | **Blender** 原生指标（面/顶点、边分类、自交面、退化几何、组件数、归一化） |
| `meta.json`（prompt、任务、缩略图） | Meshy API 返回 |

### 4.5 页面上的引擎口径说明是怎样呈现的

明细页**每行**只给"问题"（白话结论）与"判据"（阈值与量化）两行，不再逐行打印跨引擎对账结果——
旧版每行末尾都缀一句"另一划分口径下未找到对应件（尺寸/面数超出容差）"，它在 T2 的 102 条待复核
共位行里出现 **90 条（88%）**，逐行重复等于噪声，读者无从分辨（实测 p15 页 31 行里 24 行都带它）。

现在改为**每个模型页页头说明一次**，且只在两个数字真的不同时才出现：

> 另：同一模型在 Blender 焊接口径下为 107 个组件（与几何拆分口径的 144 个不同）——两套引擎的
> 焊接算法不同（邻近合并 vs 量化去重），细碎片的归并结果因此有差异，不是错误；编号与图证一律取
> 几何拆分口径。

这样读者一眼能看到"两套引擎在这一个模型上分别数出多少组件"，而不是在每一行上看到一句没有区分度的
告警。另需说明：**页面上的每一行都同时给出图证**（组件独立渲染图 + 定位图），所以任何一条检出的来源
都可以直接核对，不必依赖文字描述。

## 五、怎么跑起来

前置：`uv sync` 还原虚拟环境（Python 3.12）。所有命令在**仓库根**执行。
`uv run …` 与激活后的 `python …` 等价；本机若 `uv run` 报 trampoline 错误，直接用
`.venv/Scripts/python.exe -m …`（Windows）/ `.venv/bin/python …`（Linux/macOS）。

**A · 只想看结果（不需要 Python、不需要数据）**
双击 `publish/2026-09-22/index.html`。快照自带图证、模型与附录，完全离线；裁决按钮会
自动降级为只读。

**B · 接上数据 + 指定 Blender（一次性准备）**

代码走仓库（clone 或收到的源码目录），数据**不入库**（体积 + 可重建）、随两个 zip 分发：
`mesh-data-models.zip`（7 MB，20 个模型的
`model.glb` + `meta.json` + 缩略图）与 `mesh-data-analysis.zip`（3 MB，指标、部件特征、检出、视觉岛、
台账、`prompts.jsonl`）。每包含一份 `_pack_manifest.json`（逐文件 size + sha256，GLB 另带完整性判定），
装载时逐个校验——传输损坏会当场报出来，不会等到分析时才发现模型是坏的。

```bash
uv sync                                                  # 还原虚拟环境（Python 3.12）
cp config.example.toml config.toml                       # 补配置（见下）
python -m meshq.tools.seed_data --unpack <zip 所在目录>   # 解压到位 + 逐文件 sha256/GLB 校验
python -m meshq.tools.seed_data --check                  # 复检：各阶段输入全 OK 即装载成功
```

> 包内路径就是**仓库相对路径**（如 `data/raw/<key>/model.glb`），`--unpack` 会把它们放进正确位置，
> **不要**再手解压到别的层级；参数也可以直接给某个 zip 文件。两个包只含本交付的批次
> （T2 / smart-topology，20 个模型）：模型按目录键筛、分析产物逐记录裁剪，另一档（standard
> 对照批）的模型与记录都不在内。`--list` 可随时看本机现状。

**指定 Blender**：在 `config.toml` 的 `[blender] path` 填**可执行文件全路径**——Windows 例
`C:/Program Files/Blender Foundation/Blender 5.0/blender.exe`、macOS 例
`/Applications/Blender.app/Contents/MacOS/Blender`、Linux 例 `/opt/blender-5.0.1-linux-x64/blender`。
官网便携版 zip 解压即用、无需安装；本项目**实测 5.0.1**，4.2+ 预期可用但未实测。路径填错或留空时
`render` 会直接报「blender 可执行文件不存在：…（改 config.toml [blender] path）」，不会静默跳过；
`seed_data --check` 也会在 render 一行标注"blender 可执行未就位"。`[meshy] api_key` 只有重新生成
模型才需要，可留空。**需要 Blender 的只有渲染**——`inspect` / `detect` / `report` / `deliver` 与在线
审核全是纯 Python。

**C · 重跑渲染图并重建交付页（需要 Blender）**

```bash
python -m meshq.pipeline render                                  # 全批渲染；幂等，中断后可续跑
python -m meshq.stages.render --keys p18@smart-topology --target locator   # 只重渲某模型的某图种
python -m meshq.stages.deliver --date 2026-09-22 --out publish --snapshot  # 用渲好的图重建交付页
```

图种可单独重跑：`--target overview|highlight|wire|pieces|locator`（**改图必须加 `--force`**）。
耗时参考（单机实测）：单模型三通道约 **13 秒**（Blender 启动占大半），检出多的模型更久
（p11 有 94 件单件独立渲染 + 94 张定位图）；**全批约 30~60 分钟**。渲染经
`blender.exe --background --python meshq/blender/render_one.py` 驱动。

**渲染中间件（`data/raw/*/render`）不在数据包里**——它占了交付目录体积的绝大多数：要看图就按上面
重渲一遍，或直接读 `publish/2026-09-22/`（已入库的图证与定位图就是渲染产物）。

> 只想复核分析结论、连渲染也不想跑：`analysis` 包已是跑完的产物，直接 `deliver` 就能重建页面。
> 实测两种情形不同——**在仓库那份快照上重建**（`--out publish`）图不会掉，重建前后逐字节一致；
> **输出到空目录**则页面文字与结论齐全、但图例会留「—」占位、队列页没有缩略图（不会出现破图）。

**D · 启动项目：本地审核台（有代码 + 快照即可，不需要 `data/`）**

```bash
python -m meshq.tools.review_server publish/2026-09-22 --source publish/2026-09-22/data
# 打开 http://127.0.0.1:8000/ → 模型页首屏「入库裁决」三选一
```

提交后模型目录在 `passed/ pending/ failed/` 之间移动，队列页与模型页自动重渲染（亚秒级）；
裁决落在 `--source` 指向的 `review.jsonl`（唯一状态源，人工裁决永不被重跑覆盖）。

要重跑分析与报告（纯 Python，产物都写进 `data/`；任何阶段加 `--dry-run` 先看影响面）：

```bash
python -m meshq.pipeline inspect                 # 指标 → 部件特征 → 级联
python -m meshq.pipeline detect                  # → data/findings.jsonl（全批约十几分钟）
python -m meshq.pipeline report                  # → data/report_t2.html 等
uv run pytest                                    # 自检（343 条单测：342 通过、1 跳过）
```

**不加任何数据也能完整阅读这批结果**——模型与渲染图都在 `publish/2026-09-22/` 快照内；连数据包
也没有时，可用 Meshy API 按同一批 prompt 重新生成（**付费**，先 `python -m meshq.pipeline generate
--dry-run` 看预算再跑）。
