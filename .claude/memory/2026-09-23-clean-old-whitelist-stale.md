# `--clean-old` 白名单是手写常量 → 删掉了 1345 张现役图

- **日期**：2026-09-23
- **现象**：跑 `python -m meshq.stages.render --clean-old` 清理旧产物，它报"删除 1345 个旧图"——
  实际删掉的是**当前最新、正被交付页消费**的 `piece_*.png`（单件外观条带）
  与 `locator_*.png`（逐检出定位图）：41 个模型丢全部单件条带、25 个模型丢全部定位图，
  `data/raw` 从 2.3GB 掉到 1.5GB。交付目录与离线快照不受影响（图证已在其中转码完成）。
- **根因**：`clean_legacy` 的判据是常量 `KEEP_NAMES`，只登记了 base/highlight/wire/compare/zoom
  五个图族——那是"单件条带与定位图出现之前"的产物集。此后新增 `piece_*` / `locator_*`
  两族时**没人回来登记**，于是清理逻辑把新产物视为旧残留。
- **修复**（本轮）：
  1. 判据改为**单一来源**的 `PRODUCT_PNG_PATTERNS`（现役图族的正则表），并提供
     `is_current_product()`；`--clean-old` 的说明同步；
  2. 新增三条单测：每个现役图族都要留、旧命名要被删、json 产物（`locator_marks.json` 等）
     一律不碰——**旧测试只覆盖了 base/compare/zoom，所以这个 bug 之前测不出来**；
  3. 被删的渲染产物按 `--target pieces` / `--target locator` 重渲补齐（渲染确定性已实测：
     重渲后重建交付与已入库快照逐字节一致）。
- **预防**：**"清理白名单"与"产物集"必须同源**。任何新增图种，除了写产出代码，还要在
  `PRODUCT_PNG_PATTERNS` 登记——否则下次清理就是一次静默的数据损失。这与
  `2026-09-23-swept-artifacts-need-cleanup`（不删旧产物会污染条带）是一对**反向**风险：
  那边是"该删不删"，这边是"不该删却删"，两者的解都是"产物集只有一个权威清单"。
- **附带发现**：清理白名单之外，`--target locator` 的完成判据是 `locator_marks.json`
  （跑完最后写的产物），它**不校验对应图像是否存在**——图像被外部删除时会被误判为"已齐"，
  需要 `--force`。这条留给 PLAN-08 §三 一并处理。
- **关键词**：清理白名单, 产物集, 单一来源, clean-old, 数据损失, 完成判据
